# MVP 성공 기준 점검 (C, 2026-10-12)

7주차 설계명세서의 "MVP 시연 성공 기준"을 실제로 확인했다. Dify 콘솔 API로 초안 흐름을 실행하고(응답 스트림을 끝까지 읽어 노드·시간 기록), 승인은 폼 API로 제출, 최종 답변은 대화 기록 API로 읽었다.

| 기준 | 결과 |
|---|---|
| 질문 하나로 분석 → 선별 → 검수 → 승인 → 보고가 끝까지 동작, 학습은 미리 돌린 결과 | 통과 (S1) |
| 보고 수치가 실행 기록·결과 파일과 100% 일치 | 통과 (S1 재실행 답변의 숫자 98개 모두 일치, `curation_tools/check_report.py`) |
| 시나리오 4개 (정상 / 개수 없음 / 범위 밖 예산 / 도구 서버 꺼짐) | 4개 모두 통과 |
| 승인 대기를 뺀 응답 시간 60초 이내 | 통과 (승인 화면까지 18~22초 + 승인 후 보고 약 8초) |
| 시연 1회 비용 $0.01 이하 | 통과 ($0.0014, Dify 사용량 집계: 입력 9,517 + 출력 382 토큰, Gemma-4-26B-A4B 입력 $0.13 / 출력 $0.40 per 1M) |

| 번호 | 입력 | 기대 | 결과 |
|---|---|---|---|

## 점검하며 고친 것
- **보고에 틀 문구가 그대로 나옴**: S1 보고에 "[학습 결과] (이곳에 코드가 생성한 표와 판정이 붙습니다)"라는, 표가 들어갈 자리를 LLM이 스스로 만들어 넣었다. 지시문의 자료 칸 제목([학습 결과 상태])을 흉내 낸 것. 보고 지시문에 "대괄호 제목이나 안내 문구를 옮기지 않고, 표가 들어갈 자리를 만들지 않는다" 규칙을 추가해 재실행에서 사라진 것을 확인
- **"구분 불가"인 이유가 안 보임**: 신뢰구간이 0을 넘는데도 시드마다 방향이 달라 "구분 불가"가 된 판정(예: 같은 프레임 수 +16%p, 신뢰구간 +5~+27)에 이유를 붙였다 → "구분 불가 (신뢰구간은 0보다 크지만 시드마다 방향이 다름)"
- **검수가 선별 도구 경고를 놓침**: 선별 도구 자체 검사의 위치 쏠림 문제를 검수가 경고로 이어받게 했다 (Square에서 발견, `review.py`)

## 수치 검사기의 한계
`check_report.py`는 답변의 숫자가 "그 대화의 기록·결과 파일 어디에도 없는 값"인지 본다. 일부러 숫자를 바꿔 넣은 시험에서 4곳 중 3곳(21,834, 77%, 116)을 잡았고, +41%p는 41이 다른 기록 값에 우연히 있어 놓쳤다. 즉 기록에 있는 다른 숫자로 바뀐 경우는 못 잡는다. 학습 결과 표와 판정은 코드가 만들기 때문에 LLM이 숫자를 바꿀 수 있는 곳은 요약 몇 줄뿐이다. 1~10은 목록 번호·3x3·1주차·5%p 기준 같은 형식 숫자로 보고 검사에서 뺐다.
