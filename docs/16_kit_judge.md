# MVP 14-4단계: 학습 키트와 결과 판정 (2026-10-17)

우리는 학습을 돌리지 않는다. 사용자에게 학습 키트를 주고, 사용자가 자기 환경에서 학습한 결과 파일을 올리면 판정한다.

## 학습 키트 (`build_kit`, `curation_tools/kit.py`)
검수를 통과한 선별 결과로 만든다 (학습 계획이 없으면 먼저 만든다). 실행 폴더의 `kit/`에 저장하고 웹 `/api/kit/{실행ID}/{파일}`로 내려받는다.

| 파일 | 내용 |
|---|---|
| `<데이터>_curated.hdf5` | 고른 데이터. 원본 복사본에 묶음별 필터 키(curated_N, random_N, train 등)를 넣은 것 (선별 도구가 만든 파일) |
| `train_curated.ipynb` | "선별 데이터로 학습": 선별 묶음 1개 → 올리면 "결과 확인" |
| `train_compare.ipynb` | "선별·무작위·전체 비교 학습": 3묶음(약 3배 시간) → 올리면 "선별 효과 판정" |
| `train_settings.json` | robomimic 설정 항목 이름으로 적은 학습 설정과 평가 방법 |
| `README.txt` | 사용법 |

노트북 (Square 노트북의 설치·학습·평가 셀을 그대로 쓰고 아래만 새로 만듦)
- 0번 셀이 환경을 판단한다: Kaggle(`/kaggle/working`), Colab(`/content`), 그 밖의 리눅스(현재 폴더). 위에서부터 실행만 하면 된다
- 데이터: 키트의 데이터 파일이 노트북 옆(Kaggle은 입력 데이터)에 있으면 그 파일, 없으면 Hugging Face 원본을 내려받아 같은 묶음을 만든다. 원본이 없는 사용자 파일은 키트 파일이 꼭 있어야 한다
- 평가: 마지막 epoch 시험 100회, 중간 epoch 30회, 시험마다 시작 위치·행동 난수를 12345+i로 고정 (우리 실험과 같은 위치끼리 짝지을 수 있게)
- 실제로 쓰는 robomimic 전체 설정 파일(`robomimic_config_<묶음>.json`)도 결과 폴더에 저장한다 (로컬에 robomimic이 없어 미리 만들 수 없어서)
- 결과 파일: `curation_results/results_main_<지문>.json`

## 결과 판정 (`judge_results`, `curation_tools/judge.py`, 웹 `POST /api/results/{대화ID}`)
| 결과 파일의 묶음 | 이름 | 내용 |
|---|---|---|
| 선별 + 무작위(또는 전체) | 선별 효과 판정 | 같은 시험 위치끼리 짝지은 비교 (`train_eval.paired_report` 그대로): 무작위보다 나은지, 전체 대비 하락 5%p 이내인지 |
| 선별만 | 결과 확인 | 성공률과 95% 신뢰구간, 근거표의 비슷한 실험의 묶음별 성공률. 판정이라는 말을 쓰지 않는다 (학습이 제대로 돌았는지 점검 수준) |

- 거부하는 결과: 계획 지문이 다름, 시험 난수가 고정되지 않음, 학습 모드가 아님, 계획을 찾을 수 없음, 마지막 epoch 시험별 결과가 없음
- 학습 시드가 1개면 "시드마다 같은 방향인지는 볼 수 없어 우리 실험보다 약한 근거"라고 함께 적는다
- 사용자 결과는 우리 실험 결과(results.json)를 덮어쓰지 않고 `results/uploaded/`에 따로 저장한다. 판정은 대화 기록(`judged`)에 남아, Dify에서 "학습 결과 보여줘"라고 하면 최근 판정을 보여 준다
- 실제 결과로 확인: 예산 60 1차 결과 파일(선별·무작위·길이만·그리퍼만)을 넣으면 선별 - 무작위 +21.0%p 차이 있음 (docs/12와 같음), 선별만 남기면 결과 확인 83% (74~89%)

## 근거표에 묶음별 성공률 추가
결과 확인 화면에서 사용자 성공률과 나란히 보여 주려고 근거표 행에 선별·무작위·전체의 성공률을 넣었다. 판정·추천 개수는 그대로다 (Can 135, Square 150).

## 학습 계획을 다른 데이터에도
`prepare`가 Can·Square 말고도 목록(catalog)의 데이터(내려받을 경로 있음)와 사용자 파일(경로 없음, 키트의 데이터 파일 필요)을 받는다. 파일럿으로 설정을 정하지 않은 데이터는 Can 설정을 그대로 쓰고 결과에 그 사실을 적는다.

## 실제 실행 확인 (7단계, 2026-10-17)
사용자와 같은 경로로 핵심 줄기를 끝까지 돌렸다.
1. 실제 대화(웹 중계 서버 → 게시된 Dify)로 "can_mh에서 학습할 시범 골라줘" → 개수 확인 카드에서 추천 135개 그대로 확정 → 키트 (run `R-20261017-170255-select-ffc0`, 지문 `6c7c9de76982e590`)
2. 웹 링크에서 받은 `train_curated.ipynb`를 **고치지 않고** Kaggle T4(편집 화면 Run All)에서 실행. 키트의 데이터 파일은 일부러 붙이지 않아 **원본을 직접 내려받아 묶음을 만드는 경로**까지 확인
3. 결과 파일을 웹 결과 올리기(`POST /api/results/<대화 ID>`)로 올림 → "결과 확인" → 같은 대화에서 "학습 결과 보여줘"로 같은 판정 조회

| 항목 | 결과 전 예측 (B 실험 선별 135 시드 1) | 키트 실행 |
|---|---|---|
| 400 epoch | 90/100 | **90/100** |
| 200 epoch | 22/30 | **22/30** |
| 시험 100번의 성공·실패 | - | **100번 모두 B 실험과 같음** |

- 예측은 실행 전에 기록했다. 키트와 B 실험은 고른 시범(묶음 5개 모두)과 학습 설정이 같고, 계획 파일의 평가 횟수 값(`rollout_n` 50 대 100)만 달라 지문이 달랐다 (평가는 둘 다 시험 100회)
- 환경: Kaggle T4, Python 3.13.15, torch 2.11.0, robosuite 1.5.1, mujoco 3.3.0 (예산 60 1·2차 실험과 같음). 설치 중 pip 의존성 충돌 경고(diffusers 등)는 우리 학습과 무관하며 이전 실험에서도 같았다
- 시간: 설치 100초 + 학습 487초 + 평가 882초 + 원본 내려받기 → 약 25분

진행 중 겪은 것
- API 실행(push)은 T4 대기열에서 35분 넘게 시작되지 않아 취소하고 편집 화면에서 직접 실행했다. P100으로 바꾸지 않은 이유: 다른 GPU에서는 재현성 확인(성공 횟수까지 같은지)을 할 수 없음
- 편집 화면에서 Run All이 3번 셀 뒤에 끊긴 적이 있다 (오류 없이 다음 셀이 실행되지 않음). 자리를 비웠다가 "Continue editing"으로 세션이 다시 시작되면 처음부터 다시 실행해야 한다

이번에 고친 것
- **같은 계획 판단**: 실행 ID가 같을 때만 "같은 계획"으로 보던 것을, 고른 시범과 학습 설정(평가 횟수 값 제외)을 직접 비교하도록 고침. 같으면 같은 묶음·시드의 우리 실험 결과와 **시험별로 비교**해 결과 카드에 "시험 100번 중 100번 결과가 같음 → 우리 실험을 그대로 재현"을 표시 (`judge._same_selection`, `_seed_match`, 웹 결과 카드, Dify 판정 정리 노드)
- **예상 시간**: 키트 묶음 하나 40분 → 25분 (키트 실측, B 실험도 묶음당 약 25분). 40분은 예산 60 2차의 약한 모델 기준이었다 (실패한 시험은 제한 시간 끝까지 돌아 평가가 길어짐)

## 아직 확인하지 않은 것
- Colab과 일반 리눅스 서버에서는 돌려 보지 않았다 (경로 판단 코드만 있음)
