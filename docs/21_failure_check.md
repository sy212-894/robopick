# MVP 14: 핵심 줄기 실패 대비 점검 (2026-10-17)

교수님 기준 "좁고 깊게, 핵심 한 줄기가 입력→출력 100% 동작"에 맞춰, 7주차 설계명세서 2-6 "실패 대비" 표를 지금 흐름(v2)에서 실제로 일으켜 확인했다. 핵심 줄기: Can 데이터 → 진단 → 개수 확인(사람) → 선별·검수 → 학습 키트 → (사용자 학습) → 결과 올리기 → 판정.

모든 항목은 게시된 Dify에 중계 서버(웹 데모와 같은 경로)로 실제 대화를 보내 확인했다.

## 명세서 대응 → 실제 점검

| 실패 | 명세서 대응 | 실제로 일으킨 방법 | 점검 전 | 점검 후 |
|---|---|---|---|---|
| 도구 실패 | 재시도 2회 → 안내 후 종료 | MCP 도구 서버를 끄고 대화 | 안내 후 종료 (정상) | 그대로 |
| LLM 실패 (에이전트) | 예비 모델 Qwen으로 폴백 | Gemma 설정을 실행 중 오류가 나게 바꿔 게시 | Qwen이 이어받아 끝까지 진행 (정상) | 그대로 |
| LLM 실패 (최종 보고) | 안내 후 종료 | 보고 모델을 실행 중 오류가 나게 바꿔 게시 | **흐름 전체 오류, 이미 만든 학습 키트 안내도 사라짐** | 기본 문장으로 대신하고 키트·근거는 그대로 |
| LLM 실패 (질문 변환), 근거 검색 실패 | 안내 후 종료 | 설정 확인 | 대비 없음 (시작하자마자 오류) | 기본값으로 계속 |
| 기록·판정 도구 실패 | 안내 후 종료 | 설정 확인 | 대비 없음 | 도구 실패 안내로 종료 |
| 잘못된 인자: 범위 밖 개수 (5, 999, -3) | 서버가 거절, 이유 전달 | 개수 확인 카드에 입력 | 서버 거절이 Dify에서 "성공"으로 처리되어 검수 반려 "사유 없음" | "고를 개수는 10~270 사이여야 합니다 (입력 5개…)" |
| 잘못된 인자: 숫자 아님 ("abc", "150개") | 서버가 거절 | 카드에 입력 | 안내는 나오나 "개수 오류"로 단정 | 개수·도구 서버 확인 안내 + 오류 내용 |
| 잘못된 인자: 0 | - | 카드에 입력 | 추천 개수(135)로 고르는데 "**0개로 골랐습니다**" | "135개로 골랐습니다 · 개수 근거: 추천 (근거표)" |
| 없는 데이터 이름 (transport_mh) | 서버가 거절 | 대화 | 사용 가능한 데이터 목록 안내 (정상) | 그대로 |
| 환각 (보고의 지어낸 내용) | 숫자는 도구 결과만, 보고 숫자 대조 | 정상 대화 반복 | **보고가 가짜 코드 블록·표를 지어냄 (2번)** ("notebook_1: 전처리용") | 보고에 표 대신 요약 문장만 넘기고, 코드 블록·표를 코드로 걸러 냄 |
| 사람 거부 | 기록 후 종료 | [취소] | 기록 후 안내 (정상) | 그대로 |
| 무한 루프·시간 초과 | 반복 5회, 시간 상한 | 설정 확인 | 에이전트 반복 5회, 사람 확인 24시간 | 그대로 |
| 결과 파일 오류 (새 단계) | - | 잘못된 파일 13종을 올림 | 대부분 거절. **성공·실패 값에 2가 섞여도 판정** (성공률 부풀림), 문자열·-1은 파이썬 오류 문장 노출 | 0/1 목록이 아니면 이유와 함께 거절 |
| 키트 파일 경로 조작 (새 단계) | - | `..%2F` 경로 요청 | 거절 (정상) | 그대로 |
| 승인 뒤 화면이 멈춤 (새로 발견) | - | 반복 실행 | 가끔 승인 뒤 이어지는 흐름을 못 받아 답이 안 보임 (실제 흐름은 끝남) | 끝 이벤트를 받을 때까지 다시 구독, 끝 이벤트의 최종 답을 우선 사용 |

## 바꾼 것
- Dify 흐름: 선별 결과 없음 답변(도구의 이유 표시), 보고 정리 노드, 실제 고른 개수 표기, 보고·변환·검색 LLM의 기본값 처리, 기록·판정 도구 실패 분기. 게시본에 바뀐 노드만 더해 게시 (결과는 `dify/curation_chatflow.yml`)
- `curation_tools/judge.py`: 시험 결과가 0/1 목록인지 검사
- `curation_tools/server.py`: 개수 범위 오류 문장, 추천과 같은 개수는 "추천"으로 표기
- `webapi/dify.py`: 승인 뒤 흐름 다시 구독, 끝 이벤트의 최종 답 사용
- `curation_tools/analyze.py`: 요약의 품질 신호 목록을 실제로 쓰는 4개로 (동작 거칠기 표기 정리)

## 확인
- 테스트 75개 통과 (결과 값 검사, 다시 구독, 신호 목록 추가)
- 위 표의 "점검 후"는 모두 실제 대화로 다시 확인

## 남은 한계
- 서버 거절이 Dify에서 노드 성공으로 처리되는 성질은 Dify(MCP 도구) 동작이다. 선별 단계만 흐름에서 따로 받았고, 에이전트가 부르는 분석 도구는 에이전트가 오류 문장을 그대로 전한다
- 보고 정리는 코드 블록·표를 걸러 낼 뿐, 문장 속 숫자가 틀린 경우는 웹의 보고 수치 검사(`/api/check`)로 확인한다
